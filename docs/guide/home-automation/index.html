Home Assistant · Hubitat · Webhooks

Your scenes, running without your phone

Link AVR Maestro to Home Assistant or Hubitat and every scene you have built becomes a native script on your hub. From then on the hub talks to the receiver directly, on your own network - so "Alexa, movie night" works with your phone off, asleep, or in another country.

Why it runs without the app

Most integrations make your phone the middleman: the phone hears the command, the phone sends it, and the automation only works while the phone is awake and on the network.

AVR Maestro does not do that. It compiles your scenes into scripts that live on your hub, and the hub sends the commands to your receiver's local IP. The app's job ends when the sync finishes.

  • Local-first: nothing is routed through a MiyaraHub server. Your hub and your receiver talk to each other.
  • Phone-independent: once a scene is published it runs whether or not the app is installed on the phone that made it.
  • Your assistant, not ours: Alexa, Google Assistant and Siri Shortcuts all reach these scripts through the hub you already trust. AVR Maestro adds no voice layer of its own.

Home Assistant, start to finish

  • 1. Add your receiver to Home Assistant first. Settings › Devices & Services › Add Integration › Denon AVR (or HEOS), then your receiver's local IP. Home Assistant creates a media player entity for it.
  • 2. Open Settings › Home Automation in AVR Maestro and tap the Home Assistant card.
  • 3. Enter your Home Assistant address - a local one like http://192.168.1.150:8123, or your external Nabu Casa URL.
  • 4. Log in and authorize. A secure in-app browser opens Home Assistant's own login. Your credentials go to Home Assistant, never to us.
  • 5. It finds your receiver by itself. The app scans your media player entities and scores them on model, name and surround capability, then fills in the right entity for you.
  • 6. Sync. Your scenes are built into scripts and uploaded. After that, editing a scene updates its script in the background - there is no button to remember.
If you synced with an older build

Your script IDs change once

Scripts used to be named after the scene and the receiver, so renaming either one left the old script behind and quietly created a second. They are now named after the scene and the receiver's MAC address, which is what makes a rename update the same script instead of forking it.

The first sync after that change replaces the old scripts with the new ones. Anything you built on the old IDs needs repointing once - a dashboard button, an automation, a voice alias. Open the script in Home Assistant to find its new entity ID.

Hubitat

Hubitat is supported through its Maker API, and is marked BETA in the app because it is newer than the Home Assistant route, not because it is unfinished.

  • Hub IP - your Hubitat's address on the LAN.
  • Maker API App ID - the number in the Maker API app's own URL.
  • Access Token - issued by Maker API when you enable it.

Enable Maker API on the hub first (Apps › Add Built-In App › Maker API) and it hands you all three. Paste them in and AVR Maestro discovers your receiver, publishes your scenes as command sequences, and pushes live state back so a Hubitat dashboard reflects what the receiver is actually doing rather than what it was last told.

Webhooks

Home Assistant and Hubitat send commands to the receiver. Webhooks go the other way: when the receiver does something, tell anything else about it. Turn the receiver on and AVR Maestro posts a small message to an address you choose - that message is the webhook.

This is the one part that is not phone-independent. Your synced scenes become scripts on your hub and run whether or not the app is anywhere nearby. Webhooks are different: AVR Maestro is the thing watching the receiver, so a trigger fires while the app is open on a device that can see it. If you want something to fire with nothing running, build it on your hub around the receiver entity instead.

The four triggers

Trigger EventFires whenCan be narrowed to
Receiver Power ONThe receiver comes out of standby-
Receiver Power OFFThe receiver goes into standby-
Active Input ChangedThe selected source changesOne input, under Only trigger for input source
Scene RecalledA Scene is appliedOne scene, under Select Scene

Narrowing is what makes them useful rather than noisy. "Active Input Changed" on every input is a firehose; the same trigger pinned to the one input your projector sits on is a light switch.

The input list is the one your own receiver reports, so it already reflects any source you have renamed or hidden. The scene list is your own scenes.

Setting one up, step by step

This is the Home Assistant route, which is the one most people want. Do the Home Assistant half first - the app needs something to point at.

In Home Assistant

  • 1. Settings › Automations & Scenes › Create Automation › Create new automation.
  • 2. Add Trigger › Webhook. Home Assistant generates a long random Webhook ID for you.
  • 3. Replace it with something you will recognise - avr-power-on, avr-movie-night. Any name works as long as it is unique on your Home Assistant. Write it down; you type the same one into AVR Maestro.
  • 4. Under the webhook's settings, allow POST. That is what AVR Maestro sends. Local-only is fine - the app is on your own network.
  • 5. Add whatever you want it to do - dim the lights, close the blinds, start a scene - and save the automation.

In AVR Maestro

  • 1. Settings › Home Automation › Webhooks, then Add First Trigger - or the + button once you have one.
  • 2. Trigger Event - pick what should set it off. Choosing Active Input Changed or Scene Recalled adds a second box to narrow it down.
  • 3. Where to send it - leave it on Home Assistant. The address is already known, because you linked it earlier on this same screen.
  • 4. Webhook ID - type the same ID you used in Home Assistant. Nothing else has to match. Underneath, the app spells out the exact address it will post to - Sends to http://your-ha:8123/api/webhook/avr-power-on - so you can check it before you save.
  • 5. Save. Then press Test on the trigger in the list. Your Home Assistant automation should run immediately.
You never type a URL for the Home Assistant route. The app builds it from the Home Assistant you linked, and it looks that address up every time a trigger fires. Move Home Assistant to a new port, a new hostname, or a Nabu Casa address, and every webhook you have already made follows it. There is nothing to re-sync and no button to press.
If the sheet says Home Assistant is not linked yet, do the Home Assistant card at the top of this page first. The webhook route needs an address to build on.

Sending somewhere that is not Home Assistant

Switch Where to send it to Other and paste a full URL into Webhook URL. Anything that accepts a POST works - a Node-RED flow, an IFTTT applet, a script on a NAS, a Hubitat Maker API endpoint. That route stores the address exactly as you typed it, so if the destination moves you edit the trigger.

What actually gets sent

A small JSON body. The What it sends card on the same screen says it in plain language for the trigger you picked, so you never have to guess - and these are the field names your automation reads:

TriggerFields in the message
Receiver Power ON / OFFevent, timestamp
Active Input Changed...plus source
Scene Recalled...plus sceneId and sceneName

In a Home Assistant automation those arrive as {{ trigger.json.event }}, {{ trigger.json.source }} and so on. You can read them, or ignore them completely and just act on the fact that it fired. Most people do the second.

If you need a different shape - a service that expects its own format - open Send my own JSON instead under that card and write it there. It is folded away and marked Advanced because almost nobody needs it, not because it is discouraged.

The screen is called Webhooks because that is what they are. If you are looking for the automations that run on your hub, those are the Home Assistant and Hubitat cards above - a synced Scene becomes a script there, not a webhook here.

When a webhook does not arrive

In the order worth checking, because the first two are almost always it:

  • Press Test first. It sends the same message the real trigger does, to the same address, and tells you which of three things happened: delivered, not delivered, or skipped because the trigger's own switch is off. If Test delivers and the real event does not, the problem is the trigger - most often an Active Input Changed narrowed to an input you are not actually switching to.
  • Check the ID matches exactly. Home Assistant webhook IDs are case-sensitive and do not tolerate a stray space. The app prints the full address it will post to underneath the field - compare it with the one in your automation.
  • Check the automation allows POST. A Home Assistant webhook trigger that only allows GET silently ignores what AVR Maestro sends.
  • Check the trigger's switch is on. Each one has its own toggle in the list, and a switched-off trigger is skipped rather than failed.
  • Triggers belong to one receiver. The list you are looking at is the list for the receiver currently selected. Another receiver has its own, so a rule made here does not fire for a different room.
  • The app has to be watching. AVR Maestro is what notices the receiver changed, so nothing fires from a phone in your pocket with the app closed. That is the trade-off described at the top of this section, not a fault.
  • Webhooks are part of Home Automation. Without that unlock the triggers are visible but nothing is sent, and Test says so rather than pretending it worked.
